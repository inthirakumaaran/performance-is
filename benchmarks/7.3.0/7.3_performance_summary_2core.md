# IAM 7.3.0 Performance Test Results — Two Node 2 Core Comparison

This document compares a **two-node cluster of 2-core nodes (2N2C)** against the four 4-core
configurations published in [7.3_performance_summary.md](7.3_performance_summary.md) — Single Node
4 Core, Two Node 4 Core, Three Node 4 Core and Four Node 4 Core.

It covers all **nine scenarios** of the main summary, over the **50 – 500 concurrency range only**,
because that is the range the 2N2C runs were executed over. The 4-core figures are the same
published values, sliced to that range.

| Test Scenario | Description |
|---|---|
| OIDC Auth Code Grant Redirect With Consent | Obtain an access token and an id token using the OAuth 2.0 authorization code grant type. |
| OIDC Auth Code Grant Redirect Without Consent | Obtain an access token and an id token using the OAuth 2.0 authorization code grant type without consent. |
| OIDC Auth Code Grant Redirect Without Consent Retrieving User Attributes | Obtain an access token and an id token without consent. Retrieve country, email, first name and last name as user attributes. |
| OIDC Auth Code Grant Redirect Without Consent Retrieving User Attributes, Groups and Roles | As above, additionally retrieving groups and roles. |
| SAML2 SSO Redirect Binding | Obtain a SAML 2 assertion response using redirect binding. |
| App Native Authentication | Obtain an access token and an id token using the app native authentication flow. |
| Token Exchange Grant Type | Obtain an access token and an id token using the token exchange grant type. |
| Client Credentials Grant Type | Obtain an access token using the OAuth 2.0 client credentials grant type. |
| OIDC Password Grant Type | Obtain an access token and an id token using the OAuth 2.0 password grant type. |

## Understanding the metrics

The conventions are those of the main summary. Throughput is the rate of the **primary bottleneck
step** marked **✦** — complete end-to-end flows per second for multi-step flows, requests per second
at the `/token` endpoint for single-step grants. Response times are **95th percentile values in
milliseconds** for that same step, so both metrics describe the same gating step.

| Test Parameter | Values |
|---|---|
| Concurrent Users | 50, 100, 150, 300, 500 |
| No of Users / OAuth Applications / SAML Applications | 1000 / 1000 / 1000 |
| Token Issuer | JWT |
| RDS Instance Type | [**db.m6i.2xlarge**](https://aws.amazon.com/rds/instance-types/) |
| IS Instance Type (4 Core configurations) | [**c6i.xlarge**](https://aws.amazon.com/ec2/instance-types/) |
| IS Instance Type (Two Node 2 Core) | 2 vCPU per node — exact type not recorded in the result exports |
| Error rate (Two Node 2 Core runs) | 0% on every scenario and concurrency measured |

> **Reading the charts:** where the configurations differ by more than 8× *at the same concurrency*,
> the chart is drawn on a **log y-axis** — otherwise the four 4-core series collapse into one flat
> band against a single 2-core spike. The axis label says so on those charts; it applies to the
> response-time charts of scenarios 2, 3, 4, 6 and 8.

## Performance Test Results

### 1. OIDC Auth Code Grant Redirect With Consent

#### Obtain an access token and an id token using the OAuth 2.0 authorization code grant type.

This scenario involves **5 sequential HTTP request steps** to complete the full authorization flow
with user consent:

| Step | Description |
|---|---|
| 1. Authorize Endpoint Request | Initiates the authorization flow by calling the `/authorize` endpoint. |
| 2. Credential Submission | The user submits their username and password to the identity provider. |
| 3. Authorization Callback | The server validates credentials and issues an intermediate authorization response. |
| **4. Consent Approval** ✦ | The user approves the requested OAuth scopes. This is the primary bottleneck step under load. |
| 5. Token Request | Exchanges the authorization code for an access token and ID token. |

> A random think-time delay is applied before credential submission and consent approval to simulate
> realistic user interaction. Throughput represents **complete 5-step flows per second**.

> **Step selection caveat:** step 4 is reported here for consistency with the published summary,
> where it is the step that collapses first at high concurrency. Within the 50 – 500 range measured
> for 2N2C it is *not* the slowest step — "Get tokens" (24 – 32 ms) and "Common Auth Login"
> (24 – 29 ms) are consistently higher than the 12 – 14 ms shown below.

**Performance Comparison with 95th Percentile of Response Time (ms) — Consent Approval Step ✦**

100 | 12 | 11 | 11 | 13 | 12
150 | 12 | 11 | 11 | 13 | 12
300 | 13 | 11 | 11 | 13 | 12
500 | 14 | 13 | 11 | 15 | 15

**Throughput Comparison (Complete Flows/sec) — Consent Approval Step ✦**

Concurrent Users | Two Node 2 Core | Single Node 4 Core | Two Node 4 Core | Three Node 4 Core | Four Node 4 Core

50 | 6.20 | 6.20 | 6.22 | 6.14 | 6.22

> **Reading the throughput chart:** all five series coincide. In this range the flow is bound by the

## Scaling observations

**Scale-up beat scale-out at equal total core count.** Two Node 2 Core and Single Node 4 Core both
provide four vCPUs in total, but the single 4-core node was faster on all three machine-to-machine
grants:

| Scenario | Metric at 500 users | Two Node 2 Core | Single Node 4 Core | Difference |
|---|---|---|---|---|
| Client Credentials | Throughput (req/s) | 681.38 | 970.82 | 2N2C 29.8% lower |
| Client Credentials | 95th percentile (ms) | 2495 | 783 | 2N2C 3.2× higher |
| Token Exchange | Throughput (req/s) | 335.51 | 454.53 | 2N2C 26.2% lower |
| Token Exchange | 95th percentile (ms) | 4127 | 1759 | 2N2C 2.3× higher |
| OIDC Password Grant | Throughput (req/s) | 293.44 | 401.99 | 2N2C 27.0% lower |
| OIDC Password Grant | 95th percentile (ms) | 4079 | 1559 | 2N2C 2.6× higher |

Across the 50 – 500 range 2N2C returned 7 – 30% less throughput than 1N4C at matched core count, so
splitting four cores across two nodes cost throughput rather than adding it. Clustering overhead and
per-node capacity limits are the likely causes; this is a small set of runs, not a controlled
scale-up-versus-scale-out study, so treat the direction as indicative.

**Two cores per node saturate early on machine-to-machine grants.** On all three single-step grants
2N2C throughput peaks at the lowest measured concurrency (50 users) and falls from there — down 25%
by 500 users on Client Credentials, 27% on Token Exchange and 30% on the Password Grant. Single Node
4 Core shows the same shape but shallower (down 8 – 12%), while the multi-node 4-core configurations
hold flat or rise. A 2-core node has little headroom left even at 50 concurrent users for these
grant types.

**Interactive flows hold to 300 users, then four of six cliff at 500.** Through 300 concurrent users
every redirect-based scenario on 2N2C is at most 25 ms slower than the fastest 4-core configuration
and within 1% on throughput, because client think time — not server capacity — paces the flow. At 500
users that stops being true for the three without-consent variants (409 – 437 ms) and App Native
Authentication (465 ms), each roughly 13 – 17× the Two Node 4 Core figure, with throughput slipping
2 – 3% below the pace the 4-core clusters still hold.

**What survives 500 users is a function of requests per flow.** The two interactive scenarios that
do *not* cliff are the ones that ask least of the cluster per unit of user-visible progress:

| Scenario | Steps per flow | Flows/sec at 500 users | Resulting request rate | 95th percentile |
|---|---|---|---|---|
| SAML2 SSO Redirect Binding | 2 | 82.58 | ~165 req/s | 45 ms |
| Auth Code With Consent | 5 | 61.77 | ~309 req/s | 14 ms |
| App Native Authentication | 3 | 80.19 | ~241 req/s | 465 ms |
| Auth Code Without Consent | 4 | 80.48 | ~322 req/s | 437 ms |

SAML stays well under the cluster's knee. The with-consent flow carries an extra think-time pause,
so at 500 users it performs about 62 authentications per second against roughly 80 for the
without-consent variants — the 2-core knee sits between those two authentication rates, which is why
adding the consent step makes the flow *more* tolerant rather than less.

**Capacity guidance.** For 7.3.0 on 2-core nodes, a two-node cluster is adequate for interactive
browser-based authentication up to roughly 300 concurrent users, and for SAML redirect binding
through 500. Machine-to-machine grants are the limiting case: budget for roughly 290 – 460 req/s on
the password and token-exchange grants and 680 – 910 req/s on client credentials. Expect 95th
percentile latencies above one second from 150 concurrent users on the password and token-exchange
grants, and above two seconds on all three by 500. Where those rates matter, four cores on one node
beat two cores on each of two nodes.
